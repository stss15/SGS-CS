README_10_LEVEL_START_STATE_MODEL.md

Purpose

This document defines how each level starts from a preconfigured state so students can iterate on the current level without replaying earlier content.

This is essential for pace and sanity:
	•	students should not have to play through earlier rooms to test a small change
	•	validators need deterministic setups
	•	worksheets must be able to state exactly what the player has at the start of the level

Non-negotiables:
	•	Start state is engine-owned and deterministic.
	•	Start state assumes the “optimal prior path” has been taken (required items/flags are already in place).
	•	Start state must match what the website worksheet states.
	•	Start state must not depend on future content (not present anyway).

⸻

Concept: “Level snapshot”

Each level folder contains exactly one snapshot configuration that defines:
	•	where the player begins
	•	what items are already owned (if any)
	•	what status values are already set (health, etc.)
	•	which world flags are already set (doors unlocked, chest opened, etc.)

This snapshot is not a save system. It is a teacher-owned “starting checkpoint”.

⸻

What start state must cover

Every level must define these categories explicitly (even if empty/default):

1) Location
	•	starting room id / name
	•	optional: facing direction or position (only if the map system uses it)

2) Player status
	•	health (and any other required stats introduced by contract)
	•	any required state flags attached to the player (only if already introduced)

3) Inventory contents
	•	list of item ids/names that must already be owned
	•	optional: quantities if the inventory supports it (keep this minimal)

4) World state flags

These are engine-owned flags that represent progress:
	•	door unlocked / locked
	•	chest opened / unopened
	•	NPC talked to / not talked to
	•	encounter completed / not completed
	•	any other gate relevant to this level’s scenario

Rule:
	•	world flags must remain few and clearly named. If flags start multiplying, the design is drifting into complexity.

5) Scenario context (optional)

If the level’s scenario expects a specific situation:
	•	“boss encounter about to start”
	•	“NPC is waiting in room”
	•	“door is locked until key used”

This should be represented through world flags and controlled placements, not through complicated scripting.

⸻

Where start state lives (packaging rule)

Start state configuration must live in the engine and ship with the level folder.

Requirements:
	•	one small engine-owned config file/module per level
	•	no database
	•	no cloud
	•	no dependency on OS-specific locations

Recommended structure:
	•	engine/level/ contains the snapshot config
	•	run_game.py loads it automatically
	•	validate.py uses the same snapshot to run deterministic behaviour checks

⸻

Start state workflow (per level)

A) Website worksheet publishes the declared start state

Each worksheet must include:
	•	starting location
	•	assumed inventory
	•	assumed health/status
	•	any relevant world flags (in plain English)

B) Level snapshot matches the worksheet exactly

Before release:
	•	compare worksheet “Starting state” box to snapshot config
	•	run run_game.py and confirm the state is correct immediately on start
	•	run validate.py and confirm deterministic outcomes

C) Students only work on the current objective

Students should be able to:
	•	run the game and immediately see the scenario relevant to the level
	•	run validation without needing to “set up” the world manually

⸻

Rules for assumed progress

Because the current level starts mid-journey:
	•	the snapshot assumes that required prior events happened successfully
	•	the snapshot assumes required prior items were collected

Examples of what is allowed to assume:
	•	the player already owns a required key item
	•	a prior door is already unlocked
	•	a prior “tutorial encounter” is already completed

Examples of what is not allowed to assume:
	•	complicated branching histories (“if you chose X earlier, now Y”)
	•	multiple mutually exclusive inventory paths
	•	any prior decision that would force the engine to support two different start states

This is a deliberate simplification to prevent scope creep.

⸻

Validation requirements tied to start state

validate.py must:
	•	load the same start state snapshot as run_game.py
	•	run scripted checks from that state
	•	avoid random outcomes (or seed them)

If validation requires a particular item/flag:
	•	it must be included in the snapshot (not generated by “play”)

⸻

Handling item dependencies without branching

To prevent branching, use one of these patterns:

Pattern 1: Single required item
	•	the snapshot includes the item
	•	the level tests using it

Pattern 2: Required tool is always granted at start
	•	if the level is about using a mechanic (e.g., “use item on door”), the snapshot grants the item
	•	avoid making students re-earn the tool in this level

Pattern 3: Prior progress becomes a fixed world flag
	•	rather than tracking full history, just set:
	•	tutorial_complete = True
	•	gate_unlocked = True

If you find yourself needing many flags to represent history, the level design is too complex.

⸻

Interaction with save/load (when introduced)

If a save/load feature exists in the final game:
	•	it remains separate from the snapshot system during level iteration
	•	the snapshot is still used to start the level deterministically

Students should not have to maintain save files to validate.

⸻

Release checklist (start state)

Before publishing a level folder:
	•	Worksheet “Starting state” section exists and is clear
	•	Engine snapshot config matches worksheet exactly
	•	run_game.py starts directly in the correct state
	•	validate.py uses the same snapshot
	•	No branching start states exist
	•	Required inventory/flags are minimal and justified
	•	Start state does not expose future-level content

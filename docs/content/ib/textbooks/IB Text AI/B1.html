B1 Computational Thinking: Educator's Implementation Guide

This guide captures the full scope of the B1 curriculum for Cambridge IGCSE and IB Computer Science. It categorises content into Knowledge, Skills, and Pedagogical Boundaries.

B1: Problem Specification & System Design

1. Key Terminology

Term Definition
Stakeholder Any individual or group with an interest in the success or failure of a system (e.g. users, owners, developers).
Problem Specification Starting point of a solution; a clear definition of objectives, goals, and requirements. Used as the basis for Criterion A in IB.
Evaluation Criteria Clear, specific, and measurable metrics used to judge the success of the final product.

2. Input & Output (Knowledge)

  • Data Entry Forms:
    • Direct: Barcode scanners, OCR, OMR, and MICR (Magnetic Ink Character Recognition) readers.
    • Manual: Keyboards, joysticks, touch screens, mouse, or human operators.
    • Automatic: Sensors (Temperature, light, infrared, pressure).
  • Trade-offs:
    • Manual: Cheaper to implement but prone to human error.
    • Automatic: Expensive hardware/software but faster and more accurate.
  • Output Types:
    • Temporary: Screen displays.
    • Permanent: Hard copies (printouts).
    • Mechanical/Physical: Actuators (switches, relays).

3. Global Constraints & Limitations

When designing global systems, students must consider:

  • Regional Differences: Currencies, languages, date formats, units of measurement.
  • Legal: GDPR (Europe), consumer-protection laws, content restrictions.
  • Cultural: Colour meanings (sensitivity), UI alignment (LTR vs RTL), time zones.

B1.1.2: Pillars of Computational Thinking

1. Abstraction

  • Definition: Extracting essential information while disregarding irrelevant data to create a simplified model.
  • Programming Use: Hiding data entities via data structures or hiding implementation details (subroutines).
  • Benefits: Faster development, reduced memory/space requirements, higher customer satisfaction (no feature creep).
  • TOK Link: "The Map is not the Territory" (Generalising and naming things as a human act of abstraction).

2. Decomposition

  • Critical Distinction: Breaking down the problem into smaller parts, NOT just breaking a program into sub-programs. Decomposition happens before coding.

3. Pattern Recognition

  • Definition: Identifying similarities to support modularity and reusable code (functions/procedures).

4. Algorithmic Design

  • Definition: Finite sequence of specific, ordered instructions with predictable outcomes.

B1.1.3: Industry Applications

  • Games: Abstraction is used to filter out "misleading clues" to focus on core mechanics.
  • Data Analysis: Pattern recognition predicts market trends and automates repetitive tasks.
  • Machine Learning: Finding patterns in large datasets (e.g. identifying skills of a football player or predicting purchasing habits).
  • Databases: Decomposition for relational tables; Abstraction for identifying relevant data sources.
  • Security: Abstraction for complex security models; decomposition for cybersecurity ecosystems.

B1.1.4: Flowcharts & Tracing

1. Standard Symbols

  • Terminator (Oval): Start/End.
  • I/O (Parallelogram): Input or Output.
  • Process (Rectangle): Calculations or assignments.
  • Decision (Diamond): Selection (labeled Yes/No or True/False).
  • Connector (Small Circle): Continuing flow across multiple pages.

2. Trace Tables (Skills)

  • Used to track variable changes, decision outcomes, and final outputs.
  • Top Tip: Write the value a variable takes after every assignment, even if the value hasn't changed from the previous line.

3. Logic Concepts

  • MOD: Remainder of a division.
  • DIV: Integer division (quotient without remainder).

4. Boundaries & Common Pitfalls

  • Avoid: Teaching the internal physics of sensors. Stick to their role as inputs.
  • Avoid: OOP syntax (inheritance/polymorphism). Keep it to "hiding complexity" at this stage.
  • Warning: Ensure flowlines are connected; unlabelled decision branches lose marks.

Stage 3

Stage 3: SQL schema design

Build the standard-level two-table model first. Tagging is not part of the core schema lesson.

Teacher onlyExact target state

Teacher objective

What the class should understand before coding

Students need to see how the planning fields become tables, keys, and relationships.

Expected student output

  • A two-table ERD with users and tasks.
  • A clear primary key for each table.
  • A foreign key from tasks to users.
  • An explanation of why usernames should not be repeated in every task row.

Normalisation direction

  • 1NF: one value per field, no repeated groups.
  • 2NF: every non-key field depends on the whole key.
  • 3NF: user details belong in the users table, not repeated in tasks.

Answer key

Questions and answers for schema design

Use these answers to guide the database conversation.

Prompt for the class Expected answer / direction
Why is user_id a foreign key in tasks? Because each task belongs to one user and the username should live in the users table.
Why store status in tasks? Because completion is a property of each task record.
Why is username not repeated inside tasks? That would duplicate data and create update problems.
What is the relationship between users and tasks? One user can have many tasks; each task belongs to one user.

Constraint language to explain explicitly

  • PRIMARY KEY means the value uniquely identifies the row.
  • AUTOINCREMENT means SQLite generates the next id for us.
  • NOT NULL means the column cannot be left empty in the database.
  • DEFAULT gives a value automatically if the insert does not provide one.
  • FOREIGN KEY enforces the relationship back to the users table.

Schema build order

Step-by-step schema to write on the board

Treat the ERD and the SQL together: first agree the table idea, then write the SQL that makes it real.

Step 1

Write this in schema.sql

Write the users table first

Start with the simpler table so the class can focus on primary keys and required text fields.

CREATE TABLE users (
    -- INTEGER PRIMARY KEY AUTOINCREMENT creates a unique id for each user.
    user_id INTEGER PRIMARY KEY AUTOINCREMENT,

    -- NOT NULL means every user record must have a username.
    username TEXT NOT NULL
);

What this block does

  • This is the cleanest place to explain INTEGER PRIMARY KEY AUTOINCREMENT.
  • Tell the class that username TEXT NOT NULL means SQLite will reject a blank missing value at database level.
Step 2

Write this in schema.sql

Add the tasks table and relationship

Only add the second table once the class already understands why users is separate.

CREATE TABLE tasks (
    task_id INTEGER PRIMARY KEY AUTOINCREMENT,
    title TEXT NOT NULL,
    user_id INTEGER NOT NULL,
    priority TEXT NOT NULL,
    due_date TEXT,
    status TEXT NOT NULL DEFAULT 'open',

    FOREIGN KEY (user_id)
        REFERENCES users(user_id)
);

What this block does

  • Point at user_id INTEGER NOT NULL and connect it back to the planning decision that every task must have an owner.
  • Use DEFAULT 'open' to show that the database can enforce sensible starting state.

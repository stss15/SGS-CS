Stage 2

Stage 2: Planning the system

Translate the brief into screen structure, field choices, and a test plan that will later become evidence.

Teacher onlyExact target state

Teacher objective

What the class should do in this lesson

The goal is to turn the client problem into visible screens and a set of data decisions.

Teacher flow

  1. Show a task-list wireframe and ask what the user can see and do on that screen.
  2. Show an add-task modal wireframe and ask which fields are stored data and which are display-only labels.
  3. Map each visible input back to a likely database field.
  4. Start the test plan by turning success criteria into test statements.

Expected student output

  • Annotated wireframes showing buttons, fields, and output areas.
  • A field list linked to where each piece of data appears on screen.
  • A first draft of the test table headings and a few test rows.

Planning wireframe to show

The list screen should lead the discussion because it reveals the most important data fields and actions.

Answer key

Questions to ask and the direction to push them

These are the common prompts from the student pages with the answers you want in notebooks or class discussion.

Prompt for the class Expected answer / direction
Which fields must be mandatory? Title, assigned user, and priority. Due date can be optional in version one.
Where will the user view all tasks? On the main list screen, not inside the modal.
Where should completion happen? On the task row itself, because completion is a state change on an existing record.
What is display-only and what is stored? Buttons, headings, and layout are display-only. Title, user, priority, due date, and status are stored.
Why build the test table now? It makes success criteria measurable before the class writes code.

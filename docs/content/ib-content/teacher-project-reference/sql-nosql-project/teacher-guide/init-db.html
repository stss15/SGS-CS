Stage 3

Stage 3: Database initialisation

Once the schema exists, create the database file and seed the starting users before the web build begins.

Teacher onlyExact target state

Teacher objective

Why this sits before the Flask build

Students should understand that the database must exist before the web app can read from it.

Expected student understanding

  • The schema file defines structure; it does not create the live database on its own.
  • The initial users are seed data, not hard-coded interface content.
  • Running python init_db.py is a one-time setup step for this stage.

Questions and answers

Prompt for the class Expected answer / direction
Why separate schema.sql from init_db.py? Because structure definition and setup logic are different jobs.
Why insert users here? Because the interface needs real users to populate the assignee dropdown.
When should this script run? After the schema is written and before the app tries to query the database.

Syntax to explain

Important Python and SQLite ideas not to skip

Students will not know this syntax yet, so the teacher page needs to make the hidden meaning explicit.

Key terms for this file

CodeWhat it meansWhy it matters here
connThe live connection object to the SQLite databaseEvery execute, commit, and close call happens through this object.
sqlite3.connect("tasks.db")Open or create the database fileThis is how Python starts talking to SQLite.
conn.executescript(...)Run a whole block of SQL commandsIdeal for a schema file containing multiple statements.
conn.executemany(...)Run one SQL statement repeatedly with different valuesUseful for seeding several rows in one go.
?A placeholder for a value supplied separatelyIt avoids building SQL by string concatenation and keeps inserts safe.
conn.commit()Save the pending changes permanentlyWithout it, the inserted users may not persist.
conn.close()Close the database connectionAlways release the connection once the work is done.

Teacher explanation of placeholders

The ? symbol is not a mystery character. It marks where SQLite should safely insert the actual value from the tuple. In this file, each tuple in users has one value, so the SQL has one placeholder.

Live build order

Step-by-step code to write with the class

Build this file in short blocks and stop to explain the new Python and SQLite syntax before moving on.

Step 1

Write this in init_db.py

Import SQLite and open the database connection

Start by showing that Python needs the sqlite3 module before it can talk to the database file.

import sqlite3


def init_database():
    # conn is the live connection object to the SQLite database file.
    conn = sqlite3.connect("tasks.db")

What this block does

  • sqlite3.connect("tasks.db") returns the connection object, which we store in conn.
  • From this point onward, conn is the object that runs SQL and manages saving.
Step 2

Write this in init_db.py

Read schema.sql and execute the full script

This is where the class turns the written schema into a real database structure.

    # Open the schema file and run all of its SQL in one go.
    with open("schema.sql") as f:
        conn.executescript(f.read())

What this block does

  • with open(...) opens the file safely and closes it automatically when the block ends.
  • f.read() gives SQLite the full text of the schema file.
  • executescript() is used because the schema contains more than one SQL statement.
Step 3

Write this in init_db.py

Prepare the seed data as Python tuples

Pause here to explain that Python is just building the values that will later be inserted into SQL.

    # Each tuple is one row to insert into the users table.
    users = [
        ("Alice",),
        ("Bob",),
        ("Charlie",)
    ]

What this block does

  • Each tuple matches one row to insert.
  • The trailing comma matters because ("Alice",) is a one-item tuple, not just brackets around a string.
Step 4

Write this in init_db.py

Insert all user rows with placeholders

This is the most important syntax moment in the file because it introduces parameterised SQL.

    # executemany runs the same SQL once for each tuple in users.
    # The ? is a placeholder: SQLite safely swaps in each username value.
    conn.executemany(
        "INSERT INTO users (username) VALUES (?)",
        users
    )

What this block does

  • executemany() runs the same insert once for each tuple in users.
  • The ? placeholder is replaced by each username value in turn.
  • This is safer and cleaner than building SQL strings by hand.
Step 5

Write this in init_db.py

Save, close, and make the file runnable

End the lesson by making the script executable as a standalone setup step.

    # commit saves the changes permanently.
    conn.commit()

    # close releases the database connection.
    conn.close()

    print("Database created successfully.")


if __name__ == "__main__":
    init_database()

What this block does

  • commit() permanently saves the changes.
  • if __name__ == "__main__" means this setup only runs when the file itself is executed.

init_db.py

PYTHON Open raw file 
import sqlite3


def init_database():
    conn = sqlite3.connect("tasks.db")

    with open("schema.sql") as f:
        conn.executescript(f.read())

    users = [
        ("Alice",),
        ("Bob",),
        ("Charlie",)
    ]

    conn.executemany(
        "INSERT INTO users (username) VALUES (?)",
        users
    )

    conn.commit()
    conn.close()

    print("Database created successfully.")


if __name__ == "__main__":
    init_database()

Teaching notes for this file

  • Open the schema file and execute it before inserting any data.
  • Seed the users table so the modal select has something to show later.
  • Run the script once, then check that tasks.db now exists.

SL Stages

Teacher answer key for the standard-level journey

Stage 1

Problem specification: expected outputs

  • Core problem: staff currently track tasks across messages and spreadsheets, so ownership and status are unclear.
  • Inputs students should identify: task title, assigned user, priority, due date.
  • Outputs students should identify: task list, status display, user name, priority, due date, feedback after create/update/delete.
  • Constraints: simple browser-based interface, clear roles, minimal training, persistent data storage.
Stage 1

Success criteria answer set

  1. User can create a task with a title, user, priority, and optional due date.
  2. User list loads from storage.
  3. Tasks display in a readable list.
  4. User can mark a task as completed.
  5. User can delete a task.
  6. Completed status remains stored after refresh.
  7. Data is saved persistently in the selected backend.
  8. The interface is simple enough to use without technical knowledge.

Stage 2

Planning decisions the class should land on

  • Mandatory fields: title, user, priority.
  • Optional field: due date.
  • Where completion happens: a button on each rendered task row.
  • Why the list screen comes first: it is the main read view and determines what data must be stored.
  • Display-only UI elements: button labels, layout containers, modal shell.
  • Stored data: title, user_id, priority, due_date, status, then later tags.

Stage 3

Exact SQL core tables

Table Field Type Key role
users user_id INTEGER Primary key, auto increment
username TEXT Required
tasks task_id INTEGER Primary key, auto increment
title TEXT Required
user_id INTEGER Foreign key to users.user_id
priority TEXT Required
due_date TEXT Optional
status TEXT Default open

Why this is correct: one user can own many tasks, but each task belongs to one user in the core build. That gives a clean 1:many relationship before the tagging extension.

Stage 3

Core ERD to expect

Normalisation note: username is stored once in users. The task row stores the user_id reference instead of duplicating names across many task records.

Stage 5 + 6

Algorithm and database extension answer key

Plain-English algorithm the class should produce

  1. Take the task title text.
  2. Convert it to lowercase.
  3. Split the text into separate words.
  4. Remove common stop words such as the, a, and for.
  5. Count how many times each remaining word appears.
  6. Keep only the words that appear once.
  7. Limit the result to a maximum of three tags.
  8. Attach those tags to the task when it is created.

Exact SQL extension tables

Table Field Type Reason
tags tag_id INTEGER Primary key for each unique tag
tag_name TEXT Unique tag value
task_tags task_id INTEGER Foreign key to tasks
tag_id INTEGER Foreign key to tags; together with task_id forms the composite primary key

Why the composite key matters: the pair (task_id, tag_id) stops the same task being linked to the same tag twice.

Updated SQL ERD after tagging

The teacher explanation should be: a task can have many tags, and a tag can appear on many tasks, so the direct relationship is many:many and must be resolved with a junction table.

What changes in code when tagging is added

  • tag_algorithm.py is introduced.
  • create_task() still inserts the task first.
  • The backend then generates tags from the title.
  • For SQL: if a tag already exists, reuse its tag_id; otherwise insert it.
  • For SQL: insert each task/tag pair into task_tags.
  • For JSON: the generated tags are stored directly inside the task document as "tags": [].
{
  "task_id": 4,
  "title": "Prepare physics experiment report",
  "user_id": 1,
  "priority": "High",
  "due_date": "2026-03-10",
  "status": "open",
  "tags": ["prepare", "physics", "experiment"]
}

SQL JSON / NoSQL

Fixed schema Flexible structure
Joins handle relationships ID references or embedded data handle relationships
Strong data consistency and integrity rules Flexible but easier to duplicate data

HL Stage 3: modelling comparison answers

  • Model A: separate users.json and tasks.json with IDs reduces repeated user data and makes updates easier.
  • Model B: embedded user data can simplify reads but duplicates user information across many task objects.
  • Expected conclusion: Model A aligns more closely with the SQL design and makes the SQL/JSON comparison cleaner for students.
